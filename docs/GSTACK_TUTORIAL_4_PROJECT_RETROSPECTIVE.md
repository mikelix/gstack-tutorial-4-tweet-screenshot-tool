# Project Retrospective: Tweet Screenshot Tool (Gstack Tutorial No. 4 source material)

This document reconstructs how the Tweet Screenshot Tool was actually built, in one
continuous session on 2026-09-17, from the original request through production
deployment. It has two jobs: become the raw material for Gstack Tutorial No. 4, and
become a checklist the next project can reuse.

Everything in this document is grounded in the project's own artifacts:
`tweet-screenshot-tool-plan.md` (the CEO review + engineering review + implementation
log, written live as the work happened), `TODOS.md`, `README.md`, the source code,
`ChatGPT-gstack-20260917.pdf` (the external-mentor conversation log — see Part 1B), and
this session's own direct record of the Aside browser QA runs and their evidence
(screenshots, exported PNGs, byte sizes, console-error checks). Where something is not
independently verifiable — most notably the human's own manual testing, which by
definition only the human can confirm — it is marked as **reported by the user**, not
claimed as AI-verified. Where a plan-level intention was never actually implemented in
code, that gap is called out explicitly rather than smoothed over.

This was not a two-party build. It was a three-layer collaboration: a human founder,
an external AI mentor persona running in a separate ChatGPT session, and the gstack
team of specialist AI roles running inside Claude Code. Part 1B documents that meta-agent
layer in detail, because it materially shaped almost every phase below — most of the
"optimized prompts" that drove the CEO review, the engineering review, the 14-phase
implementation, the Aside-browser strategy, the mid-project debugging correction, and
the rapid-finalization/ship decision were drafted by that external mentor, not typed
from scratch by the human or generated by gstack itself.

# PART 1 — Executive Summary

## What we built

Paste a tweet URL → the app fetches the tweet server-side → renders a pixel-perfect
live preview → you customize it (background, padding, export scale, light/dark theme)
→ download it as a PNG, copy it to your clipboard, or copy a shareable link that
restores the tweet for someone else.

A second mode (`/thread`) does the same thing for a manually-assembled list of tweets:
add each tweet's URL in order, reorder or remove them, and export the whole stack as
one combined PNG.

- **Production URL:** https://tweet-screenshot-tool.vercel.app
- **Stack:** Next.js 16 (App Router, TypeScript), `react-tweet` (tweet rendering via
  X's free public syndication endpoint — no paid API), `modern-screenshot` (DOM→PNG
  export), Vercel (hosting).
- **Major external dependencies:** `cdn.syndication.twimg.com` (undocumented, unowned,
  the single point of failure for the entire product — see Part 4), the `react-tweet`
  and `modern-screenshot` npm packages.
- **Known limitations (real, not hypothetical):** a thread share-link's style
  (background/padding/theme) doesn't reliably restore on first load, even though the
  tweets and their order always do (root cause not found — see Part 4 and `TODOS.md`);
  no rate limiting yet on the two public API routes; video/emoji/multi-image export and
  real-Safari clipboard behavior are implemented but not empirically verified.
- **Final ship verdict:** SHIP WITH KNOWN LIMITATIONS. Both core flows (single tweet,
  thread) were verified working in production via real-browser automation and reported
  by the user as manually tested and visually confirmed.

This document follows that same distinction throughout and refers to the persona as
**"AI Garry Tan"** — an OpenAI GPT persona, not the actual person, not an official YC

## Why the user ran a second AI alongside gstack

The PDF opens with general questions about gstack's own design (its seven AI-native-company
principles, its role-separation philosophy, its `/browse` + Aside browser capabilities)
before narrowing onto this specific project. Once the tweet-screenshot-tool work began,

produce a decision point — often its own `AskUserQuestion`-shaped output, sometimes a
long architecture-review or implementation-status block — the user would paste that
output into the ChatGPT conversation, and AI Garry Tan would (a) explain it in plain
language (its own "ELI10" convention), (b) give an opinionated recommendation, and (c)
hand back a ready-to-paste message for the user to send to gstack. The user then
relayed that message back into Claude Code, largely verbatim.

**What the PDF directly documents**, in chronological order of the actual exchanges:

## The persona challenged and structured gstack rather than replacing it

Every instance above followed the same shape: AI Garry Tan never generated application
code, never touched the repository, and never talked to gstack directly — it only ever
produced text the human chose to relay. In multiple cases it explicitly disagreed with
or refined gstack's own framing before handing back an answer (the html2canvas
correction, the "no secrets" → "one small infra credential" correction, insisting on a
preview-before-production deploy sequence even though gstack's own draft prompt already
asked for that, adding the "verify with the actual DOM, not the accessibility snapshot"
caution that later proved correct in Phase 7's real testing). It functioned as a review
and drafting layer sitting *above* gstack's own specialist roles, not as one more
specialist inside them.

## Why this resembles a CEO / chief-of-staff / meta-orchestration layer

This is interpretation, not something the PDF states explicitly, but the pattern maps
cleanly onto a role familiar outside AI: a chief of staff (or a fractional CEO advisor)
does not do the engineering, sales, or QA work of the company. They read what each
function reports, translate it into a decision the founder can actually make quickly,
draft the message that goes back down to the team, and periodically intervene when a
function is stuck (the debugging-thrash intervention) or moving too slowly relative to
the goal (the ship-mode pivot). AI Garry Tan occupied exactly that seat here: one level
above gstack's own CEO/PM/architect/reviewer roles, orchestrating *when* and *how* the
human engaged with them, without ever being one of them itself.

## Where human judgment remained essential

The external-mentor layer did not remove any of the human gates already documented in
Part 2 and Part 6 — it added one more layer of *drafting*, not one less layer of
*deciding*. Concretely, across the whole PDF the human still: manually relayed every
message between the two separate AI systems (no automated bridge existed between
ChatGPT and Claude Code); chose, every time, whether to accept AI Garry Tan's
recommended option (the "I would choose Option 1" pattern) or ask a follow-up first;
performed the actual Vercel account login and Aside browser authorization themselves,
in their own browser, because neither AI system could or should do that; and did the
human-in-the-loop manual testing and visual PNG inspection that Part 2 already marks as
the one AI-irreplaceable gate. The mentor made the human faster and more precise at
each of those decisions — it did not make any of them for the human.

## Why this matters for Gstack Tutorial No. 4

The teachable claim here is specific, not general "two AIs are better than one" hype:
a meta-agent layer is valuable exactly to the extent it (a) translates a specialist
AI team's raw output into a decision a time-constrained human can actually evaluate,
(b) drafts precision prompts that make the specialist team's *next* action more
efficient than the human's own first attempt at prompting would have been, and (c) is
willing to contradict or correct the specialist team when its own review surfaces a
gap — as it did on html2canvas, on "no secrets," and on the debugging-thrash
intervention. A tutorial chapter on this project should show at least one full example
of that translation (the `/plan-eng-review` charter is the clearest, since its
before/after is fully documented: a bare `/plan-eng-review` invocation versus the
12-point charter that actually produced the PROCEED WITH FIXES verdict).

## Reusable pattern for future projects

```
Human founder / learner
      ↓
External AI mentor / meta-agent (separate session, separate provider)
      ↓
Optimized, structured task prompt
      ↓
gstack specialist role (inside Claude Code)
      ↓
Evidence (code, test output, browser QA, exported artifact)
      ↓
Human gate (relay the evidence back to the mentor, or decide directly)
      ↓
Next stage
```

This is also reflected in Part 8's reusable checklist (item 11) and Part 6's
human/AI-responsibility table.

# PART 3 — Timeline of the Project

### Product definition

**Goal:** decide what to build and on what foundation, before writing any code.
**Important decisions:** single tweet first, manual thread builder (not automatic
discovery), no paid X API, no scraping-dependent architecture, Next.js on Vercel.
**Risks discovered:** the two closest existing open-source competitors (Twimage,
Laureate) are both built on the official X API, which has had no free tier since
2026 — meaning they're effectively non-functional for a free tool today. This was
*verified* via web search, not assumed.
**Evidence produced:** CEO review Step 0 (premise challenge, implementation
alternatives, dream-state mapping).
**Decision:** proceed with `react-tweet` + `modern-screenshot` on Next.js/Vercel,
explicitly rejecting both "fork a dead-API app" and "server-side headless-browser
screenshot" as alternatives.

### Export architecture

**Goal:** pick the actual mechanism for fetching and rendering a tweet without a paid
API. **Important decisions:** `react-tweet` for rendering (fetches via X's public
syndication endpoint), `modern-screenshot` for the DOM→PNG step. **Risks discovered:**
the syndication endpoint blocks direct browser CORS requests — verified live, not
assumed — meaning a server-side hop is structurally required. **Evidence:** a live
probe against the real endpoint, cited in the plan's Step 0E. **Decision:** Next.js
Route Handlers reuse `react-tweet`'s own server-side fetching pattern rather than
hand-rolling a proxy.

### CEO review

**Goal:** stress-test the plan before committing engineering time. **Major findings:**
an SSRF hole in the not-yet-built image proxy (host-substring matching would have let
`evil-twimg.com.attacker.net` through); a silent-wrong-output race between font loading
and PNG capture; a stale-response race if a user changes their mind about which tweet
to load mid-fetch; thread mode redefined mid-review from "auto-stitch" to "manual
multi-URL" once it became clear no free data source can discover a thread's next
tweet. **Decision:** proceed to the outside-voice pass.

### Outside-voice challenge

**Goal:** get a second, independent-context pass before locking the plan. **Most
important cross-model tensions:**
- **Rate-limit/shared-state contradiction (OV-1):** the plan claimed "no secrets," but
  real per-IP rate limiting on stateless serverless functions requires shared state
  (Upstash/Vercel KV) — a real, if small, infra credential. Accepted; the plan's "no
  secrets" claim was corrected in-place rather than left standing.
- **Safari clipboard user-gesture issue (OV-2):** the approved clipboard-copy fix
  (await fonts, await capture, then write to clipboard) would break on Safari/iOS,
  which requires `navigator.clipboard.write()` to fire within the same synchronous
  gesture chain as the click. Accepted; the fix became "pass a `Promise<Blob>` directly
  into `ClipboardItem`, never await first."
- **Video-export ambiguity (OV-3):** what does "export a video tweet" even mean for a
  static-image tool? Accepted: force the poster frame, add a small play-icon badge so
  it reads as intentional.
- **URL length ceiling (OV-4):** thread mode's URL-encoded share state had no cap, and
  a real thread can run past what a URL can safely carry. Accepted: hard cap at ~12
  tweets with an explicit message, never silent truncation.
- **Premature DRY/shared-component assumption (OV-7):** the plan asserted "TweetCanvas
  will obviously be shared between single-tweet and thread modes" before any thread
  code existed. Softened to an explicit re-evaluation checkpoint rather than treated as
  settled — this is revisited for real in Part 4/Phase 8 below.
**Decision:** 6 of 8 tensions accepted outright, 1 softened, 1 skipped as low-value
given independently-verified evidence.

### Engineering review

**Goal:** is the reviewed plan actually buildable as written? **Findings:**
- The image-proxy "fix" from the CEO review was never actually connected to any real
  DOM element — `react-tweet` renders plain `<img>` tags pointing straight at
  `pbs.twimg.com`, and nothing in the plan rewired that. This is the single most
  important finding in the whole project (B1) — see Part 4.
- The proxy's SSRF hardening was still incomplete: no redirect re-validation, no
  protocol check, no response-size cap, no MIME validation (B2).
- Two more silent-wrong-output paths the CEO review hadn't caught: no wait for images
  to finish decoding before capture (same bug class as the font race), and emoji
  rendering was never named in the test plan at all (B3).
- The rate-limiter (from OV-1) had no defined failure behavior — if it fails closed on
  an Upstash outage, a second infrastructure dependency takes the whole app down even
  though the already-accepted X-endpoint SPOF is fine (B4).
- Thread mode's per-tweet vs. whole-thread styling scope was never decided, which also
  affects the URL-length cap math (B5).
**Implementation sequencing change:** inserted a new step, T1.5, before any broad
Route Handler code — a spike specifically to verify the image-proxy wiring question
with real code instead of more planning.
**Decision:** PROCEED WITH FIXES — start implementation immediately, following the
revised task order.
**Meta-agent note:** the `/plan-eng-review` invocation that produced this whole review
did not run bare — it ran against the 12-point charter the External AI Mentor drafted
when the user explicitly asked for "the optimized prompt... not just `/plan-eng-review`"
(see Part 1B). That charter is what specified the A–H output format, the "do not begin
coding during this review" rule, and the instruction to mark uncertain dependency
behavior as "VERIFY DURING IMPLEMENTATION" rather than inventing certainty.

### T1.5 spike

This is the most important phase in the whole project, and it earns the extra detail.
It ran as part of the same 14-phase implementation instruction the External AI Mentor
drafted (Part 1B) — the mentor's prompt is what named this specifically as a
*mandatory* spike gating T3/T5, not an optional nice-to-have.

**Why it was inserted:** the engineering review's B1 finding was a real, unresolved
technical unknown — not a product question, a *does this actually work* question. The
project's explicit operating principle for implementation was "build evidence, not
volume," and this was exactly the highest-risk assumption to de-risk first.

**How `react-tweet`'s DOM/media was actually inspected:** not from documentation or
memory — by reading the installed package's real compiled source
(`node_modules/react-tweet/dist/twitter-theme/*.js`) directly. This showed that
`EmbeddedTweet` accepts a `components` prop that can override how avatars and media
images render, and that `TweetMediaVideo` renders a real `<video poster={...}>` element
with the poster URL already present as a live attribute — no separate lookup needed.

**How `modern-screenshot`'s `fetchFn` was verified:** same method — reading
`node_modules/modern-screenshot/dist/index.mjs` directly. This showed `fetchFn(url)` is
called for every remote image during capture, and its return value is consumed exactly
like the library's own `responseType: "dataUrl"` fetch path — a fact that turned out to
matter enormously (see the bug below).

**How the video `onCloneNode` behavior was discovered:** the same source-reading pass
showed `modern-screenshot` exposes `onCloneNode`/`onCloneEachNode` hooks that fire on
the *cloned* DOM tree right before rasterization — the natural place to swap a `<video>`
element for an `<img>` pointing at its poster frame without touching the live,
interactive page.

**Why DOM rewriting was not needed:** because `fetchFn` intercepts assets at
*capture time only*. The live, on-screen preview keeps pointing straight at real
`pbs.twimg.com` URLs (which is fine — cross-origin images display normally; the
CORS restriction only bites when a canvas tries to *read* their pixel data). Only the
capture step needed to route through the SSRF-hardened image proxy, so `react-tweet`'s
`components`-override mechanism, while genuinely available, ended up not being needed.

**The actual bug discovered:** the first real capture attempt passed the "no exception
thrown" bar — `modern-screenshot` reported success — but the exported PNG showed a
broken-image icon where the avatar photo should have been. Everything else (text, font,
gradient background, rounded corners) was correct. This is a textbook silent-wrong-
output failure: the code "worked" by every naive check and still produced the wrong
result.

**Root cause, found by reading source, not guessing:** the image-proxy route itself was
tested directly and confirmed working (`200 image/jpeg`, valid binary data). The bug
was in how the proxy's response was handed back to `modern-screenshot`: the fetch
wrapper (`proxyAwareFetch`) returned a `blob:` object URL via `URL.createObjectURL()`.
That works fine for a normal `<img src>`, but `modern-screenshot` serializes the cloned
DOM into an SVG string and reloads *that* as a fresh image resource to rasterize it —
and a `blob:` URL created in the live document does not reliably resolve once embedded
inside that re-loaded SVG resource.

**The fix:** return a self-contained base64 `data:` URL instead (`FileReader
.readAsDataURL()`), matching exactly what `modern-screenshot`'s own
`responseType: "dataUrl"` contract expects.

**How the fix was proven, visually:** the corrected PNG was saved to disk and read
directly with an image-viewing tool — Jack Dorsey's real profile photo appeared,
correctly circular-cropped, in place of the broken-image icon. Capture time also
dropped (1046ms → 468ms), a secondary confirmation that a slower, failing code path had
been replaced with a faster, working one.

### Main implementation

Single-tweet flow: URL input, live preview, background/padding/scale/theme
customization, download/clipboard/share-link export controls, a tweet-shaped loading
skeleton, stale-request protection (an `AbortController` + request-token pair — the
later of two racing requests always wins, verified with a deterministic network-delay
test, not luck), and versioned URL state with `popstate` back/forward support (verified
against real DOM attributes after Aside's own `goBack()`/`goForward()` wrapper turned
out not to support pushState-based SPA routing — a tooling limitation caught and worked
around, not an app bug).

Thread mode: a manual multi-URL builder, independent fetch-per-item, reorder,
duplicate-prevention, retry, remove, an inline error card that blocks export until
resolved (never silently drops a failed tweet from the export), and a shared style
across the whole stack.

### Aside browser QA

Aside — an AI-native real browser — had already been installed on this Windows 11
machine by the user in a prior session, along with its command-line automation
interface, which the user explicitly asked this project to use instead of installing a
separate headless-browser stack (Playwright/Chromium). Aside became the real-browser
QA tool for the entire project: every checkpoint from the T1.5 spike through the final
production smoke test was driven through it, including exporting real PNGs and reading
them back to visually confirm correctness, injecting a real network delay to force a
deterministic race condition, and directly querying DOM attributes as ground truth when
Aside's own accessibility-snapshot rendering of `aria-pressed` turned out to be
unreliable for one component (a tooling quirk caught mid-session, not a real app bug).

The explicit rule to use Aside instead of installing Playwright/Chromium did not
originate from a one-line user preference alone — the External AI Mentor drafted the
full instruction (Part 1B), including "if Aside fails, STOP and report why rather than
automatically switching browser engines unless I explicitly approve the fallback,"
which is the exact rule this session followed when a rejected `npm install -D
playwright` tool call was abandoned in favor of the already-verified `aside` CLI.

### Human-in-the-loop testing

**This is reported by the user, not independently verified by the AI — that is exactly
the point.** The user stated they launched the app locally, used Aside directly to open
`localhost`, tested the UI themselves, exported a PNG, and visually inspected the
downloaded file. Later, after production deployment, the user reported doing the same
against the live Vercel URL and confirming the result looked correct.

Why this matters: every AI-run test in this project (typecheck, lint, build, Aside
automation, byte-size checks, even the AI reading an exported PNG file to visually
inspect it) verifies that the *program behaves as specified*. None of it can verify
that the *result is actually good* — that a real tweet screenshot looks right, feels
right, is something a person would actually want to share. That judgment call is
irreducibly human.

project explicitly switched modes: stop open-ended debugging, document non-blockers
instead of chasing them, remove diagnostic code, clean up starter-template residue

a real, reproducible bug in thread share-link style restoration was investigated for

| Problem | Who/What Found It | Why It Was Dangerous | Fix | Status |
|---|---|---|---|---|
| CORS blocks direct browser fetch of tweet data | CEO review, live probe against the real syndication endpoint | Would have made the entire "no paid API" architecture non-functional if discovered after code was written | Server-side Route Handler reuses `react-tweet`'s own fetch pattern | **Fixed before ship** (architectural, never became a runtime bug) |
| SSRF via unrestricted image-proxy URL fetch (host-substring matching) | CEO review Section 3 / eng review B2 | Classic, actively-scanned-for vulnerability class; could leak infra secrets or turn the server into an anonymizing relay | Exact-hostname allowlist, https-only, redirect re-validation, response-size cap, MIME check | **Fixed before ship**, verified live (bad host → 400, non-HTTPS → 400, legit host → 200) |
| Image-proxy fix never wired to real DOM (eng review B1) | `/plan-eng-review`, then confirmed empirically in the T1.5 spike | The plan's own SSRF-hardened proxy would have simply never been used by the real capture path — a "fix" that fixes nothing | Discovered `modern-screenshot`'s `fetchFn` hook via reading its source; wired it to the proxy | **Fixed before ship**, with visual proof |
| **Avatar rendered as a broken-image icon despite a "successful" capture** | T1.5 spike, Aside-driven real capture + visual PNG inspection | The single clearest example in this project that a function returning without throwing is not proof of correct output | `blob:` object URL → base64 `data:` URL, root-caused by reading `modern-screenshot`'s actual source | **Fixed before ship**, with before/after visual proof |
| Silent wrong font if capture fires before web fonts finish loading | CEO review Section 2 (2A) | Wrong output, zero error signal — the worst class of bug | `await document.fonts.ready` before capture | **Fixed before ship** (implemented per plan; not separately stress-tested under artificial font delay — see `TODOS.md`) |
| Same silent-wrong-output class for images not finished decoding | Eng review B3 | Same reasoning as the font race, one layer down | `await Promise.all(images.map(img => img.decode()))` | **Fixed before ship** (implemented; not separately stress-tested under artificial image delay) |
| Stale network response overwrites a newer one | CEO review Section 4 (4A) | User changes their mind about which tweet to load mid-fetch; the *older* response could win the race and show the wrong tweet | Request-token + `AbortController`, only the latest request's response is ever applied | **Fixed before ship**, verified with a deterministic network-delay test (not luck) |
| Safari/iOS clipboard-copy breaks the user-gesture chain | Outside-voice OV-2 | The clipboard-copy feature, added specifically for its delight value, would silently fail on a large share of real browser traffic | `ClipboardItem` wraps a `Promise<Blob>` directly, never awaited first | **Implemented, NOT empirically verified** on real Safari/iOS — in `TODOS.md` |
| Video-tweet export behavior undefined | Outside-voice OV-3 | Would have shipped as "whatever frame the browser happens to paint," randomly | Poster-frame swap + play-icon badge via `onCloneNode` | **Implemented, NOT empirically verified** against a real video tweet — in `TODOS.md` |
| Thread share-link URL length unbounded | Outside-voice OV-4 | Could silently produce a broken/truncated share link on a thread's best use case | Hard cap at ~12 tweets with an explicit in-UI message | **Implemented**; exact-boundary cases (just below/at/over the cap) not empirically exercised this session |
| Silently dropping a failed tweet from a thread export | CEO review Section 11 (11A) | Would misrepresent a conversation with no indication anything was cut | Inline error card, export blocked until resolved or removed | **Fixed before ship**, verified via Aside (valid → invalid → valid sequence, remove resolves it, export re-enables) |
| Rate-limiter/shared-state contradiction ("no secrets" vs. real rate limiting) | Outside-voice OV-1 | Would have shipped rate limiting that silently does nothing (in-memory counters reset every cold start on serverless) | Plan corrected to use Upstash/Vercel KV, fail-open on backend errors | **Planned and reviewed, NOT implemented in code** — see Part 5's core lesson; documented in `TODOS.md` as a security-adjacent gap |
| Thread share-link *style* (not tweets/order) doesn't reliably restore | Phase 8 browser checkpoint, this session | Cosmetic but real and reproducible; undermines confidence in the shareable-link feature | Investigated for one bounded pass (including a full dev-cache clear); root cause not found in the time allotted | **Documented, deferred, NOT fixed** — in `TODOS.md`, explicitly marked as a known non-blocking issue |

**The central lesson of this table:** the avatar bug is the strongest example in this
project of the fact that **a successful function call is not proof of correct output.**
`modern-screenshot` reported success. No exception was thrown. And the image was still
wrong. Only reading the actual pixels of the actual exported file caught it.

# PART 5 — Evidence Ladder

Weakest to strongest, as this project actually climbed it:

1. **Idea** — "people want to screenshot tweets nicely." Removes zero uncertainty about
   feasibility.
2. **Architecture assumption** — "a Next.js proxy should work around the CORS block."
   Removes uncertainty about *intent*, not about whether it's *true*.
3. **Code compiles** (`tsc --noEmit`) — removes uncertainty about type correctness.
   Says nothing about runtime behavior.
4. **Unit/component test** — not actually written for most of this project's logic
   (see Part 7); would remove uncertainty about isolated function behavior.
5. **Local browser behavior** — the T1.5 spike's first capture attempt "succeeded" at
   this level and was still wrong. This is the level that most convincingly *looks*
   like proof and most often isn't.
6. **Aside real-browser test with a deterministic setup** (e.g. the network-delay race
   test) — removes uncertainty about a *specific, hard-to-reproduce* failure mode by
   making it reproducible on demand.
7. **Exported PNG visually inspected (by the AI, reading the file)** — this is what
   actually caught the avatar bug. Removes uncertainty that "no error" means "correct
   output."
8. **Human manual test** — removes uncertainty that automated checks, however careful,
   share the AI's blind spots. Reported by the user in this project, not independently
   verifiable.
9. **Production deployment** — removes uncertainty about "works in dev" vs. "works with
   real infrastructure, real network conditions, a real domain."
10. **Human production test** — removes the last gap: does the *actual shipped thing*,
    not a close cousin of it, hold up.

**The core principle, and the one this project's central bug exists to teach: do not
confuse implementation with evidence.** Writing the code that should fetch and rewrite
an avatar image is not evidence that the avatar renders correctly. Only climbing to
level 7 was.

A second, related principle this project surfaced on its own: **do not confuse a
reviewed plan with a shipped implementation.** The rate-limiting fix (OV-1) climbed all
the way through CEO review, outside-voice review, and engineering review — and was
still never actually written into the code. A plan decision is not evidence of
anything past level 2 on this ladder until it's built and tested.

# PART 6 — Human vs. AI Responsibilities

| Task | AI Best Suited | Human Best Suited | Why (as this project demonstrated it) |
|---|---|---|---|
| Reading a library's real compiled source to verify an API contract | ✅ | | Reading `node_modules/modern-screenshot/dist/index.mjs` line-by-line to find the `fetchFn` contract is exactly the kind of exhaustive, patient verification AI does well and a human would (reasonably) skip |
| Detecting a race condition and constructing a deterministic test for it | ✅ | | The stale-request race was made *reproducible on demand* via network-delay injection — turning a rare, hard-to-catch bug into a repeatable check |
| Security review of a new public endpoint (SSRF, allowlist correctness) | ✅ | | Systematic, checklist-driven, exactly where AI's exhaustiveness beats human attention span |
| Running the same 3-command QC loop (typecheck/lint/build) dozens of times through a long session | ✅ | | Repeatable, mechanical, zero fatigue cost for an AI |
| Driving a browser through dozens of real-world test scenarios | ✅ | | Aside automation did this at a pace and consistency a human clicking through the UI by hand could not match |
| Vercel account login/authorization | | ✅ | A real credential-granting action tied to the human's real account — the AI explicitly declined to attempt this without the human completing it first |
| Judging whether an exported tweet screenshot actually *looks good* | | ✅ | The AI can confirm a PNG is non-empty and contains the right pixels in roughly the right place; it cannot judge "does this feel right to share" the way the person who's going to use the tool can |
| Deciding when a bug investigation has gone on long enough | | ✅ | The thread share-link style bug was investigated by the AI across many tool calls without resolution; the human's explicit "spend at most one short isolation pass... then ship" instruction is what actually ended it |
| Deciding the project is ready to move from "review" to "build" | | ✅ (with AI input) | Every scope decision, mode selection, and review-finding remedy in this project went through the user via `AskUserQuestion` — the AI proposed, the human decided |
| Translating a specialist AI team's raw output into a precision prompt for its next step | ✅ (a *different* AI — the External AI Mentor, not gstack itself) | | The External AI Mentor drafted the `/plan-eng-review` charter, the 14-phase implementation instruction, the Aside-priority rule, and the Ship Mode prompt (Part 1B) — a task well-suited to AI, but not to the *same* AI that is also doing the underlying specialist work, since that AI reviewing its own output loses the independence the CEO review's own principle ("don't let the same process invent the idea, implement it, and declare its own work correct") depends on |
| Relaying messages between two separate AI systems, and choosing whether to accept either one's recommendation | | ✅ | No automated bridge existed between the ChatGPT mentor session and Claude Code — every prompt crossed that gap because the human copied and pasted it, and could have stopped or edited it at any point |

**The principle this project demonstrates directly: humans handle consequential
authorization and subjective product judgment; agents handle repeatable technical
work — including the kind of repeatable work (exhaustive source-reading, deterministic
race-condition construction, byte-level PNG inspection) that's easy to underestimate as
"a human could do that too, eventually," when in practice the human wouldn't, and
didn't need to.**

**A second principle this project adds, specific to the two-AI structure documented in
Part 1B: an independent AI reviewing another AI's output is more valuable than the same
AI reviewing itself — but that independence still routes through a human relay, not an
automated one, and the human's approval remains the gate on every exchange in both
directions.**

# PART 7 — Where We Wasted Time

Candidly, the two places this session spent real time without a proportional payoff:

**The thread share-link style-restoration bug.** This consumed the largest single
block of investigation time in the project: React state was directly confirmed correct
via temporary instrumentation on every render, yet the rendered DOM attribute was still
wrong — a genuine, reproducible paradox that survived a Strict Mode on/off test, a full
Turbopack cache clear, and a dev-server restart. In hindsight, the right move would have
been to timebox this *before* it consumed as many tool calls as it did, rather than
after — the eventual instruction to stop and document it in `TODOS.md` was correct, and
should have arrived (from either side) sooner. **Lesson for next time: set an explicit
time/attempt budget on any single bug investigation *before* starting it, not after it's
already run long.**

**No automated test suite was actually written.** The plan called for unit tests (URL
parsing, state encode/decode), component tests, and mocked integration tests for every
API route's error paths (Section 2's full registry). None of that was built — every
verification in this project happened through manual Aside-driven browser checks
instead, gated on finding real, currently-live tweet IDs for each scenario (a text
tweet, an image tweet, a long-text tweet). That's a slower, less repeatable way to get
the same evidence, and it's the direct reason items like "emoji rendering," "multi-image
tweet," and "video tweet" remain unverified in `TODOS.md` — a mocked test could have
covered them in minutes; hunting for a real, still-live tweet matching each case by hand
could not keep pace. **Lesson for next time: for a project whose plan already specifies
a mocked-test strategy, write at least the cheapest layer of it (URL parsing, state
encode/decode — pure functions, no browser needed) early, rather than relying entirely
on manual browser QA for everything.**

A smaller, genuinely low-cost inefficiency worth naming: this session's environment had
an inconsistent `bash` (missing on first use, present but missing basic coreutils like
`sleep`/`tail`/`find` later, apparently a different minimal shell each invocation) —
several commands failed and had to be redone through PowerShell instead. This cost a
handful of tool calls, not a large amount of time, and wasn't something either side
could have anticipated or fixed.

# PART 8 — Reusable Checklist for the Next Project

Distilled from what actually worked here, not generic advice:

1. **Before choosing an architecture, verify the one fact most likely to invalidate
   it — live, not from memory.** This project's entire shape hinged on "the X API has
   no free tier" and "the syndication endpoint blocks browser CORS." Both were checked
   against the real world before a line of code was written.
2. **Run a CEO-level review, then a genuinely independent second pass, then an
   engineering review — in that order — before implementation starts.** Each layer in
   this project caught things the previous one missed (SSRF → Safari clipboard →
   image-proxy wiring gap). Skipping any one layer would have shipped a real bug.
3. **When a plan-level fix depends on an unverified library API contract, insert a
   spike before building the surrounding system at full scope — and make the spike
   produce visual evidence, not just "no exception thrown."** T1.5 is the clearest
   example in this project of a process step that directly prevented a real, silent bug
   from reaching users.
4. **Treat "the function returned without throwing" as the *start* of verification, not
   the end.** Climb the evidence ladder (Part 5) as far as the risk warrants — for a
   pixel-output feature like this one, that means actually looking at the pixels.
5. **Use a deterministic setup to reproduce a race condition on demand, rather than
   hoping to catch it by luck.** The stale-request race was only reliably provable once
   network delay was artificially injected.
6. **Distinguish a reviewed decision from a shipped implementation, explicitly, before
   calling something done.** The rate-limiting gap in this project survived three
   review passes and was still never built — catching that gap required checking the
   actual code, not the plan document.
7. **Never let the AI perform account authorization.** The human logging into Vercel
   themselves, in their own terminal, was the one non-negotiable human gate in the
   deployment sequence — and the right one.
8. **When a bug investigation isn't converging, set (or accept) an explicit stop
   condition before it consumes disproportionate time — and document what's known,
   not just what's unresolved.** The thread share-link bug's `TODOS.md` entry records
   exactly what was verified (ids/order restore correctly) and what wasn't (style),
   which is more useful to whoever picks it up next than either silence or a vague
   "known issue" note would have been.
9. **Human visual/product judgment is a distinct, required step — not a formality after
   AI testing passes.** This project's ship decision explicitly rested on the human
   having launched the app themselves and looked at a real exported PNG, separate from
   every automated check that came before it.
10. **Write the cheapest layer of the planned test suite (pure-function unit tests)
    early, even if full E2E coverage waits.** This project's biggest process gap (Part
    7) was skipping this and paying for it later in slower, ID-hunting-bottlenecked
    manual QA.
11. **Consider running a second, independent AI mentor in a separate session
    specifically to draft the prompts that go into the specialist team — not to do the
    specialist work itself.** Part 1B documents this project's own use of exactly that
    pattern: an external mentor that reviewed gstack's outputs, corrected specific
    errors before they propagated (the html2canvas claim, the "no secrets"
    contradiction), and — critically — was willing to tell the human to stop a
    debugging session that had stopped converging, something the AI doing the
    debugging itself was not positioned to notice from the inside.
12. **Use the reusable pattern from Part 1B for any project with a specialist AI
    team:** `Human → External AI mentor/meta-agent → Optimized prompt → gstack
    specialist role → Evidence → Human gate → Next stage`. The mentor should never
    touch the repository or the specialist team directly — every exchange should cross
    through a human decision, which is what kept this project's actual account
    authorization, deployment, and final ship judgment in human hands throughout.
