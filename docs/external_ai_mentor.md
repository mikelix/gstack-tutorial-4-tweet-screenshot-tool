# The External AI Mentor / Meta-Agent Layer

> Referenced from every review in `reviews/`. This is the cross-cutting
> layer, documented once here rather than repeated five times.

## What it is, and what it is not

A separate ChatGPT conversation (`garrytan_gstack_coding_project_No4`,
exported in full as `ChatGPT-gstack-20260917.pdf`) ran alongside this
project's gstack/Claude Code session. Its persona introduces itself, in its
own first message, as *"Mentoring mode: AI-Native CEO + Research-to-Product
Translator. I'm an AI mentor inspired by public Garry Tan and YC principles,
not the real Garry Tan or an official YC representative."* This document
calls it **"AI Garry Tan"** throughout, consistently: an OpenAI GPT persona,
not the actual person, not an official YC communication, and not part of
gstack itself.

## Why a second AI, and how the loop actually worked

```
Human founder / learner
      |
External AI mentor / meta-agent (separate session, separate provider)
      |
Optimized, structured task prompt
      |
gstack specialist role (inside Claude Code)
      |
Evidence (code, test output, browser QA, exported artifact)
      |
Human gate (relay the evidence back to the mentor, or decide directly)
      |
Next stage
```

Concretely, repeated throughout the project: gstack would produce a decision
point (often its own `AskUserQuestion`-shaped output, sometimes a long
review block). The human pasted that output into the ChatGPT conversation.
AI Garry Tan explained it in plain language, gave an opinionated
recommendation, and handed back a ready-to-paste message. The human relayed
that message to gstack, largely verbatim. No automated bridge existed
between the two systems — every message crossed the gap because a human
copied and pasted it, and could have stopped or edited it at any point.

## Where it corrected gstack rather than just approving it

This is the load-bearing claim, and it's the one worth verifying rather than
taking on faith: the mentor did not just rubber-stamp gstack's own
recommended options.

| Correction | What gstack had gotten wrong | What the mentor changed |
|---|---|---|
| html2canvas claim | Plan asserted "html2canvas is dead" | Softened once a maintained fork was found — this is the kind of small factual overreach that erodes trust in a plan if it survives unchallenged |
| "No secrets" architecture pillar | Plan claimed no infra credentials needed | Corrected once real per-IP rate limiting was shown to require shared state (Upstash/Vercel KV) — a genuine, if small, infra dependency |
| Export-timeout test coverage | Plan's test gate named only font-loading races | Flagged that image-loading races needed the same coverage, not fonts alone |
| The debugging-thrash intervention | gstack's own debugging session had run ~35 minutes / ~99k tokens with no isolated root cause | *"I would stop this current debugging run now and reset the debugging method"* — an intervention the AI doing the debugging was not positioned to make about itself |

## The four prompts that actually drove this project

Each of these was authored by the mentor, not typed from scratch by the
human or generated by gstack's own default prompts. Each is the literal
source of a structure that shows up later in `reviews/`:

1. **The `/plan-eng-review` charter** — a 12-point review scope (architecture
   integrity, external dependency risk, export correctness, security,
   async/data-flow correctness, component/API design, implementation
   sequencing, testing strategy, failure modes/observability, deployment
   feasibility, simplicity/over-engineering, scope discipline) and the
   required A-H output format. This is what `reviews/03-eng-review.md`'s
   engineering pass actually ran against.
2. **The 14-phase implementation instruction** — Phase 1 (baseline) through
   Phase 14 (ship decision), the mandatory T1.5 spike, the 20-case Mandatory
   Export Checkpoint, and 10 Engineering Operating Rules, closing with
   *"Start now with Phase 1 and T1.5. Do not proceed past the mandatory
   export checkpoint until you report the evidence."*
3. **The Aside-browser-priority instruction** — *"use Aside as the primary
   browser for all interactive browser work... do NOT install or launch a
   separate Chromium... if Aside fails, STOP and report why rather than
   automatically switching browser engines unless I explicitly approve the
   fallback."* This is the direct origin of a rejected `npm install -D
   playwright` call later in the session — the rule held under real pressure
   to route around it, not just in the abstract.
4. **The rapid-finalization "Ship Mode" prompt** — stop deep debugging,
   minimum release QC only, Aside rapid smoke test, accept existing
   verification debt, clean the product, remove prototype debris, rapid
   production check, deploy, final ship report — plus 10 Ship Discipline
   rules ending in *"Once the core flow passes build + Aside smoke test,
   SHIP."*

## Where human judgment stayed non-negotiable, even with the mentor in the loop

The mentor added a layer of *drafting*, not a layer of *deciding*. Across
the whole project the human still: manually relayed every message (no
automated bridge existed); chose, every time, whether to accept the
mentor's recommended option or ask a follow-up first; performed the actual
Vercel account login themselves, in their own terminal; and did the
human-in-the-loop manual testing and visual inspection that no AI system —
mentor or gstack — could substitute for.

## Why this belongs in Tutorial No. 4 specifically

Tutorials #1-#3 taught: one AI team, verified by a mechanical gate chain,
signed off by a human. This project adds a genuinely different layer: **a
second, independent AI whose entire job is translating the first AI team's
raw output into the next precision prompt, and who is structurally
positioned to catch what the specialist team can't catch about itself** —
the html2canvas overreach, the "no secrets" contradiction, and especially
the debugging-thrash intervention, which by definition could not have come
from inside the debugging session itself.

The general principle, stated once so it doesn't need re-deriving in every
review: **an independent AI reviewing another AI's output is more valuable
than the same AI reviewing itself — but that independence still routes
through a human relay, not an automated one, and the human's approval
remains the gate on every exchange in both directions.**
